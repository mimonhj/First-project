# Kraken Seas, Stage 2 review and fixes

After Stage 2's five rounds, five reviewers played the new features like a child on a phone and on a keyboard (battle core, the Voyage III seas, the Kraken, ashore with a Stage-3-like town wiring, and the live game plus robustness), each area with a skeptic where the usage limits allowed. Fixers then re-checked every finding before fixing it, and added a regression check that fails on the old code. Usage limits and container restarts cut several agents off; they resumed from their progress notes, and the coordinator published the last verified work.

## Review findings (verbatim)

### battle:F1: Thumb-slide steering sticks after a second touch on the steering pad: the ship keeps circling and the arrow buttons stop working

- Severity: major
- Where: src/main.js: startSlide / moveSlide / endSlide (about lines 5416-5442) and playerTurn (about line 4002). The ship's-wheel handlers (touchWheel pointerdown / wheelInput / wheelLetGo, about lines 5470-5500) have the same single-pointer overwrite.
- Repro: Set the viewport to 390x844 with touch and load ?quality=low&kraken=1 (no recipes needed). Start any Act I/II level, for example __game.newGame(2), and wait for the fly-in to end. Finger A presses the left arrow and drifts 12 px or more sideways, which is normal thumb wobble, so a slide starts and the needle shows. While A is still down, finger B touches the right arrow, or the gap between the arrows. Lift both fingers in either order. Then hold the right arrow with a fresh finger.
- Evidence: The probes are /tmp/claude-0/-home-user-First-project/7f649d8c-67e4-5236-a80e-5e9eae321fb4/scratchpad/kraken/review2/battle/p2.cjs and p2b.cjs; they send real multi-touch through CDP Input.dispatchTouchEvent. p2b.cjs output: 'A holds < with a wobble' gives steer 0.732. 'all fingers up' gives steer 0.732, left false, right false, turn 0.732, so the ship keeps turning left with no finger down. 'holding > 2 s' gives right true but turn still 0.732, and the heading kept turning left by about 1.84 rad. 'paused' gives steer null: only a pause, a new slide or the next level start clears it. p2.cjs shows the same thing: after both fingers lift, a 3 s wait turned the ship about 1.9 rad, and a later tap on the right arrow left steer at 0.554. Screenshot I looked at: /tmp/claude-0/-home-user-First-project/7f649d8c-67e4-5236-a80e-5e9eae321fb4/scratchpad/kraken/review2/battle/shots/p2-stuck.png, where the rudder needle is still shown tilted with no finger on the pad. Cause: startSlide() overwrites slide.id with the new pointer. The second pointer never became an active slide, so endSlide() for it does not clear input.steer, and the first pointer's end is ignored because its id no longer matches. playerTurn() returns input.steer ?? buttons, so the stale value wins over the arrows. The wheel has the same pattern but only drops the turn rather than sticking it (p5b.cjs): with A holding the wheel at 80 degrees, a second finger touching the wheel snaps it to 0 (steer 0), and A's further drags are ignored until every finger lifts. Two-finger arrow drumming, for example with the phone flat on a table, is a natural way for a child to steer.
- Suggested fix: Track one pointer at a time. In startSlide(), return when slide.id !== null, so a second touch never takes over. Alternatively, if a slide is active when another pointer starts, set input.steer = null and showNeedle(null) first. In endSlide(), clear input.steer whenever the slide that ends was active. In the wheel's pointerdown, ignore a new pointer while wheel.id !== null. Add a controls/battle check: slide on the left arrow, add a second touch on the right arrow, lift both, and assert __game.turn.input === 0.
